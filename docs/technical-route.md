## 0. TL;DR

The project has a complete UI skeleton and a conceptual prototype, but **the frontend and backend are not actually connected, and several metrics are hardcoded fake values**. Before adding any new features, the first milestone must be: *make the app run on any real machine, show real hardware, and measure real numbers*.

The three most critical breakages:

1. **Broken IPC**: the frontend calls a non-existent REST service via `fetch('/api/...')`, while Tauri's mechanism is `invoke()`. Moreover, `@tauri-apps/api` and `@tauri-apps/cli` are not installed at all, so the desktop app cannot currently be built.
2. **Dual-engine drift**: compatibility math exists twice — `src/lib/compatibility.ts` (TS, complete) and `src-tauri/src/compatibility/calculator.rs` (Rust, simplified) — already inconsistent, guaranteed to drift.
3. **Fake data**: benchmark TTFT (0.65 s) and prompt speed (75 tok/s) are hardcoded constants; non-macOS machines report "Generic CPU/GPU"; the frontend's `DEFAULT_HARDWARE` fallback silently displays a fake M1 Pro when detection fails.

Route summary: **M0 Make it run → M1 Measure it right → M2 Windows first-class → M3 Runtime ecosystem → M4 Local history → M5 Community database** (maps to README Phases 1–5).

## 2. Target architecture

```text
┌────────────────────────── Frontend (React + TS) ──────────────────────────┐
│  Presentation only: HardwareCard / ContextSlider / ModelExplorer / …      │
│  No business logic; calls typed IPC bindings                              │
└───────────────┬───────────────────────────────────────────────────────────┘
                │ invoke() (type-safe TS bindings generated by tauri-specta)
┌───────────────▼──────────────── Rust core (src-tauri) ────────────────────┐
│  hardware/   platform probes: trait Probe → macos.rs / windows.rs / …     │
│  models/     model DB load & validation (database/models/*.json bundled)  │
│  engine/     compatibility engine (single implementation): memory → tier  │
│              → explanation → speed estimate                               │
│  benchmark/  runner state machine + ollama.rs (HTTP, streaming) + later   │
│              lmstudio.rs etc.                                             │
│  store/      benchmark history (JSON file until M3; SQLite from M4)       │
└───────────────┬───────────────────────────────────────────────────────────┘
                │ http://localhost:11434 (Rust-side reqwest; no CORS concerns)
        ┌───────▼─────────────────┐
        │ Ollama / LM Studio / llama.cpp │
        └────────────────────────┘
```

Design principles (aligned with the README):

- **Compute in one place**: all estimation/decision logic lives in Rust; the frontend only renders.
- **Single source of types**: Rust structs are authoritative; TS types are generated, eliminating hand-written drift.
- **Single source of model data**: `database/models/*.json` is the only model metadata authority.
- **Local-first**: zero network dependency in core features; Ollama is loopback-only.

## 3. Key design decisions

### D1 Communication: Tauri IPC only (revised)
- Add `@tauri-apps/api` (runtime) and `@tauri-apps/cli` (tooling).
- ~~Generate bindings with `tauri-specta` v2~~ **Revised (2026-09-30, shipped in M1)**: hand-written TS mirror types instead — Rust structs use `#[serde(rename_all = "camelCase")]` with field names matching the frontend interfaces one-to-one; type drift is guarded by the golden fixture snapshot test (engine output compared against a committed JSON fixture, doubling as the serialization contract). tauri-specta can be revisited once the toolchain and dependency matrix stabilize.
- Remove all `fetch('/api/...')`; no extra REST layer.

### D2 Compatibility engine: single implementation in Rust
- Create `src-tauri/src/engine/` (replacing `compatibility/`) with a pure entry point:

```rust
pub fn evaluate(model: &ModelSpec, hw: &HardwareInfo, ctx: usize, quant: Quant) -> CompatibilityReport
```

- **Port** the more complete TS formulas (GQA-aware KV, buffers, bandwidth-table speed estimate) into Rust, then delete the TS version. Golden-file unit tests land with the port (see §6).

### D3 Model DB: `database/models/*.json` as the only source
- Versioned schema (`"schema": 1`), fields per §4.2; bundled at build time, serde-loaded and validated at startup with clear errors.
- Delete `src/data/models.ts`; the frontend fetches the model list over IPC.
- Grow to ~20 models covering all size tiers: Qwen3 (0.6B/1.7B/4B/8B/14B/30B-A3B), Llama 3.2/3.3, Gemma 3 (4B/12B/27B), Phi-4, Mistral 7B, DeepSeek-R1 distills. MoE models must record both total and active params (§4.2).

### D4 Benchmark methodology (core of M1)
The current `stream: false` request cannot yield TTFT; the hardcoded values must go:

1. **Warm-up**: one short request (`num_predict: 16`) to absorb cold model load; discarded.
2. **Measured run**: `stream: true`, fixed `temperature: 0`, `seed: 42`, `num_predict: 128`, fixed prompt.
   - **TTFT** = time first token-bearing chunk arrives − request sent time;
   - **Prefill speed** = `prompt_eval_count / prompt_eval_duration` (final JSON frame);
   - **Generation speed** = `eval_count / eval_duration` (final frame);
   - Record whether a model load occurred (should not, after warm-up).
3. **3 runs, report median + min/max** to expose variance.
4. Error taxonomy with actionable messages: runtime not running / model not installed / timeout.

### D5 Hardware detection: trait + per-platform implementations
```rust
pub trait Probe { fn detect(&self) -> Result<HardwareInfo, ProbeError>; }
```
- `HardwareInfo` must gain: `osVersion`, `freeMemoryBytes` (real values, mandatory), `gpus: Vec<Gpu>` (multi-GPU), `Gpu.vram_bytes`, and justified `backends` (Metal/CUDA/ROCm/Vulkan/CPU).
- macOS: keep sysctl; real GPU chip name later via `IOReport`/`system_profiler`.
- Windows (M2, `windows.rs`, **shipped**):
  - CPU/RAM: `sysinfo` (the `wmi` crate is deliberately not introduced; CIM queries run through a windowless PowerShell child process);
  - GPU three-stage probe: NVIDIA via `nvml-wrapper` (feature `nvml`, default on, compiled only on Windows) → all vendors via DXGI enumeration with the `windows` crate (name / dedicated VRAM / vendor id, skipping software render drivers, largest dedicated-memory adapter wins) → driver version via PowerShell CIM; `Win32_VideoController.AdapterRAM` is never used as VRAM (32-bit wrap above 4 GB);
  - CUDA detection: successful NVML init.
- Linux (end of M2): `/proc/meminfo`, `lspci`, `nvidia-smi`.

### D6 Speed estimation: always labeled "estimated"
- Decoding is memory-bandwidth-bound: `tok/s ≈ η × BW_eff / weights_GB` (η≈0.9 empirical; quantization mixing folded in).
- `BW_eff` from a per-chip table (`database/hardware/bandwidth.json`: Apple M-series, mainstream NVIDIA/AMD/Intel); unknown chips fall back to a conservative 50 GB/s and the UI says so.
- Prefill is compute-bound; v1 gives **no** prefill estimate (better absent than fake).
- Estimated vs measured values must be visually distinct; any real measurement overrides the estimate for that machine+model.

### D7 Storage: defer SQLite
- No database through M0–M3. Append benchmark history to `app_data_dir()/history.json` (record = `BenchmarkResult` + hardware fingerprint + timestamp).
- Introduce `rusqlite` (bundled) + migrations at M4, when the comparison view creates real query needs. The README's SQLite claim materializes then.

### D8 Packaging & CI
- `npx tauri icon` to generate the full icon set, fixing the missing `tauri.conf.json` references.
- GitHub Actions three-OS matrix: `cargo fmt --check`, `clippy -D warnings`, `cargo test`, `tsc --noEmit`; tag-triggered `tauri build` with artifact upload.

## 4. Module specs

### 4.1 Hardware probe layer

Target `HardwareInfo` (camelCase to the frontend):

```text
platform: "windows"|"macos"|"linux"
arch: "x86_64"|"aarch64"
osName, osVersion
cpu:  { model, coresPhysical, coresLogical, arch, isAppleSilicon }
memory: { totalBytes, freeBytes, isUnified }
gpus: [ { name, vendor: nvidia|amd|intel|apple|unknown, vramBytes, isIntegrated, driverVersion } ]
backends: [ { kind: metal|cuda|rocm|vulkan|cpu, detail } ]
```

### 4.2 Model DB schema (v1, shipped: flat fields)

```jsonc
// Mirrors the frontend AIModelDefinition; currently a single file with 25 models.
// Nested arch and MoE (activeParamsB) are deferred to v2.
{
  "schema": 1,
  "models": [{
    "id": "qwen-3-8b",
    "name": "Qwen 3 8B Instruct",
    "family": "Qwen",
    "parameterCountBillion": 8.2,
    "layers": 32, "heads": 32, "kvHeads": 8, "headDim": 128,
    "maxContextLength": 40960,
    "supportedQuantizations": ["Q3_K_M","Q4_K_M","Q5_K_M","Q8_0","FP16"],
    "defaultQuantization": "Q4_K_M",
    "ollamaName": "qwen3:8b",
    "description": "…",
    "recommendedUse": "…"
  }]
}
```

- Speed estimation currently uses `totalParamsB` only (no MoE in the database yet; switches to `activeParamsB ?? totalParamsB` once v2 lands).
- Currently one file, `database/models/models.json` (25 models); splitting into per-model files awaits collaboration scale. Rust-side validation already covers unique ids, quantization validity and architecture sanity.

### 4.3 Compatibility engine spec

Memory model (output order matches the explanation):

```text
weights_gb  = totalParams × 1e9 × bpw(quant) / 8 / 2^30          // bpw from table; Q4_K_M ≈ 4.85
kv_cache_gb = 2 × layers × kvHeads × headDim × ctx × bytesPerElem / 2^30   // fp16 = 2B; GQA via kvHeads
overhead_gb = runtime base (table: ollama ≈ 0.5) + 0.02 × totalParams
buffers_gb  = min(1.5, max(0.2, heads × headDim × ctx × 4 / 2^30))
total_gb    = weights + kv + overhead + buffers
```

Tier thresholds (v1; centralized in `thresholds.rs` for tuning):

```text
available = unified ? totalRam × 0.75          // macOS wired-limit heuristic
          : min(vram + 0.6×(totalRam−freeRam), …)  // v1 simplification: VRAM-first
total ≤ 0.90 × available              → 🟢 recommended
total ≤ available                     → 🟡 runnable
total ≤ available + 0.5 × totalRam    → 🔴 not_recommended (swap-dependent)
otherwise                             → ⚫ incompatible
```

- Output must include `bottleneck: vram|ram|context|backend|none` plus structured advice (e.g. "dropping context to 8K reaches 🟢"), backing the README's explainability principle.
- Windows and macOS are modeled separately: discrete GPUs impose a hard VRAM constraint with optional offload to system RAM; unified memory uses the wired limit. This is the core of M2.

### 4.4 Benchmark runner state machine

```text
runtime online? → model installed? → warm-up (discarded)
→ 3 × { streaming request → TTFT / prefill / gen metrics }
→ median summary + min/max → return + append to history
```

Command signatures (exported via specta): `run_benchmark(modelId, opts) -> BenchmarkReport`, `check_runtime() -> RuntimeStatus`, `get_history() -> Vec<BenchmarkRecord>`.

### 4.5 Frontend adjustments

- Rewrite `api.ts` as a thin wrapper over the generated bindings; component structure unchanged.
- Replace the `DEFAULT_HARDWARE` fake fallback with explicit loading / detection-failed (with retry) states.
- Model cards show "estimated" and "measured" side by side (when measured exists), with distinct badges.

## 6. Testing & quality strategy

- **Golden-file engine tests** (highest priority): 3 virtual machines (8 GB Mac mini, 16 GB M1 Pro, 32 GB + RTX 4070) × 3 models (0.6B / 8B / 30B-A3B) × 2 quants = 18 snapshot assertions. Any formula change visibly touches snapshots in review.
- Upper layers tested against mock `Probe`s; platform implementations get smoke tests only (fields non-empty).
- CI (§D8) on three OSes; a mismatch between committed `bindings.ts` and regenerated output fails the build — preventing type drift.
- Gates: `clippy -D warnings`, `cargo fmt --check`, `tsc --noEmit`.

## 7. Risks & open questions

1. **License**: `Cargo.toml` already says MIT while the README defers the choice. Formalize MIT (and the `LICENSE` copyright line) soon so contributors aren't left waiting.
2. **Windows VRAM reporting**: `Win32_VideoController.AdapterRAM` is a 32-bit value (unreliable >4 GB); NVML/DXGI are mandatory — document this trap.
3. **MoE & multimodal**: MoE weight/speed split is in the schema; multimodal (vision encoders) is out of scope for v1, labeled "text-only estimate".
4. **Ollama quants vs bpw table**: actual bpw of pulled models may differ from the table (readable from `/api/show` → `quantization_level`) — add a M1 correction step "runtime-reported wins".
5. **Bandwidth table maintenance**: the chip table keeps growing; keep it a community-PR-able JSON data file, never code constants.
